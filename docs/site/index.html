imp guide

A home for your agents. A chief-of-staff plans the work, hands it to specialist agents, and stops for your go-ahead at fixed checkpoints. Every project extends the same base.

What imp is

imp (Idea-to-Merge Pipeline) is a Claude Code plugin. It holds the parts that are the same for every kind of work: the chief-of-staff, nine specialist agents, the idea lifecycle, the checkpoints, and the evidence rules. Each project fills in its own details in one settings file, .imp/project.md: where ideas live, where the code is, how data gets run, what decks look like, and who reviews between stages.

Install and connect

Once per machine

imp needs python3 on your PATH. In Claude Code, and restart afterwards:

/plugin marketplace add prompath/imp
/plugin install imp@imp

Once per project

/imp-init

It reads the project's CLAUDE.md and README.md, drafts .imp/project.md, and shows you the draft. Slots it couldn't find are marked # default. Nothing is written until you approve. Commit the file with the project so your other machines get it.

On a new machine

/ideas --projects --scan ~/Projects

This finds every connected project and adds it to this machine's list (~/.config/imp/projects.txt). Idea state travels with each project's git repo.

Updating imp

Run claude plugin marketplace update imp, then claude plugin update imp@imp, and restart Claude Code. Maintainers raise version in .claude-plugin/plugin.json for each release.

Commands

CommandWhat it does
/idea <description>Starts an idea. The chief-of-staff picks a workflow and says why, creates the idea's STATUS, looks around (read-only), then shows the G1 plan and waits.
/continue [id]Resumes an idea at its current step. It never skips a gate.
/notes [id] <notes>Files your meeting notes into the feedback log, updates decisions and assumptions, and proposes the next plan.
/ideas [--all] [--<stage>] [--waiting W] [--group G] [--projects] [--scan DIR]Lists open ideas in this project, or in every project with --projects. Done and shelved ideas are hidden unless you pass --all or a stage flag such as --done or --pitch. --waiting user and --group Pricing narrow the list.
/investigate <case>Checks whether a result is a misunderstanding, a code bug or a rulebook gap. A plain question about the data goes to the analysis workflow instead.
/save [id]Saves progress on the idea this session is working on: updates STATUS with the open decisions, commits only that idea's files, and prints the /imp:continue <id> line. With no id, it works out the idea from this session's activity, or from idea files with uncommitted changes.
/imp:push [note]Commits the repo's changes, summarizes everything unpushed, and pushes once you say yes. Under push_forbidden it commits and hands you the push command.
/imp:notion setup <page> | sync [id] | cleanupSyncs imp ideas one way (imp to Notion) into an existing tracker with Areas, User Requests and Tasks databases. setup finds the three databases on the page you name, adds imp's properties and two views (Timeline, imp pipeline), and maps each idea group to an Area. One idea is one User Request; its rounds and open questions are Tasks. sync shows a create/update/unchanged/closed list and writes only after your yes. It writes only rows with an imp key and only imp's properties, so Priority, Owner, Mandays and your hand-made rows stay yours. It never deletes; cleanup lists stray Tasks and trashes only the ones you confirm. Only projects with notion: on are exported, and only each idea's own file.
/imp-initConnects the current project.
/imp:retro [session]Runs a retrospective on a coding session (this one by default) and suggests changes to the agent's environment, most severe first: navigation, automated checks, coding standards, steering files, tool economy and information access. Adapted from mattpocock/skills.
/imp:dashboard [--port N]Starts a local page at http://127.0.0.1:8765/ (if it isn't already running) that lists every registered project's ideas in four groups: Waiting on you (a permission prompt, a session waiting for your reply, or waiting_on: user, with the gate), In progress (a live session, with its running agents), Idle (nothing live, backlog/shelved, or 7+ days without an update) and Done (behind a "show finished" box), plus stat tiles, a gate track, a sequence diagram per idea and a 60-minute state timeline, under an animated banner. It refreshes every 5 seconds without reloading the page. The same server also serves /rooms, a pixel campus of who works where, with a Zoom button and an Ideas chooser (see below).
Why /ideas and /notes? Claude Code already has built-in /status and /feedback commands. You can also just describe what you want in plain words; the chief-of-staff routes it and says which workflow it picked.

IDs: /ideas prints each idea's id. Every command accepts part of one (lapsing → lapsing-voucher). If two ideas match, it asks. Without an id, /notes goes to the idea waiting on a meeting.

The idea lifecycle

This is how work moves with the business team: pitch at the weekly meeting, experiment in rounds, ship, monitor it in production when something needs watching (checks on set dates until a monitor_until date), document. A personal idea follows the same stages, with you as the meeting.

Gates

Gates are fixed in the base. Project settings can add checks, but they can't remove a gate.

How it works inside

The chief-of-staff is a skill that runs in your main Claude Code session. The specialists have no Agent tool, so all handing-out of work happens there, next to the briefs and gates. Each specialist gets a short structured brief (goal, input files, relevant settings, constraints, output path), never the whole conversation. It writes its result to a file in the idea folder and returns a short summary.

Agents

AgentToolsWritesNotes
business-researcherread, web, writeresearch-business.mdbusiness case, psychology, other companies' examples, execution assumptions listed separately
tech-researcherread, web, writeresearch-technical.mdpapers, designs, trade-offs, a POC proposal
code-investigatorread, read-only shellcode-findings.md (saved by the chief)locations, code vs rulebook, per-case verdicts
data-analystread, write (no shell)queries/, sizing.mddrafts only; you run everything
builderread, edit, shellcode, change-summary.mdSonnet, Opus for hard steps; commits to exp/*, fix/* and feat/* only; never pushes
verifierread, shellverify.md (saved by the chief)runs local tests, reports failures only; fixes nothing; runs before the reviewer
claim-checkerread, web fetchclaims-check.md (saved by the chief)opens each cited link and checks it supports the claim; the reviewer blocks on bad ones
presenterread, write, exportdecks/numbers only from sizing.md; wording follows evidence
reviewerread, read-only shellreview.md (saved by the chief)PASS or BLOCK on plans, decks and code; always Opus; runs project extra checks

Evidence levels

Every claim in research, plans and decks carries one:

LevelMeansHow it's worded
VerifiedOur code or data, with location or queryStated plainly
SourcedExternal, with a link"Evidence suggests…", with the source
InferredReasoning from the aboveHedged: "likely", "we expect"
AssumedNo evidenceOnly on the assumptions slide

Business-execution assumptions (channels, timing, who contacts the customer, what happens after a promotion) always get their own section in G1 and their own slide in every deck. The reviewer blocks any deck that hides one.

Any markdown file under the ideas folder with waiting_on in its frontmatter is an idea. That's how /ideas finds them, including flat research notes.

The no-push hook

The plugin ships a check that runs before every shell command Claude makes. It blocks git push, gh pr create/merge/… and PR API calls when the target folder matches the project's push_forbidden globs. It checks the current folder, cd <dir> && … and git -C <dir>. Everything else passes untouched, and projects without the setting aren't affected.

Command (in acme-analytics)Result
git push inside projects/x/service-xBlocked
cd projects/x/service-x && git pushBlocked
gh pr create inside a cloneBlocked
git commit, git status, gh pr view inside a cloneAllowed
git push at the acme-analytics root (notes repo)Allowed by the hook; agents still push only when you ask
The hook reads the command text, so a push hidden inside a script or alias would get past it. The prompts forbid pushing too; the hook is a second line of defence, not the only one.

The activity hook and the dashboard

STATUS is only written at steps, so it can't say what's running right now. A second hook (hooks/activity.py) runs on session, prompt, tool, subagent, notification and stop events and keeps one small file per session in ~/.config/imp/activity/: the idea it's on, its state (working, needs_permission, waiting_reply, ended) and its running agents. Only the main session links itself to an idea, when it touches a file in the idea's folder or hands out a brief headed Brief: <role> for <id>; a subagent's own file reads don't relink it. The hook never prints, never blocks, and only rewrites the file when something changed or every 10 seconds. Each hook command exits 0 when its script is missing, so a checkout without the hook file can't block your tool calls. /imp:dashboard reads these files plus every STATUS; a session silent for 10 minutes counts as ended, and files older than a day are deleted. STATUS also has a gate field, set while an idea is stopped at a gate and cleared once you pass it, so the page can say which gate is waiting.

Above the panels, a small animated banner shows the overall mood: waiting on you beats working, which beats idle. Pick its character in the top bar (fish, train or ants; the choice is kept in the browser). The same character plays every mood: the fish school across while agents work, blow ? bubbles when something waits on you, and drift when all is quiet; the train stops at a red signal labelled with the most urgent gate. It pauses in a hidden tab and stays still if your system asks for reduced motion. The anthill is drawn as tiny pixel blocks rather than block characters, because browsers draw block characters at uneven sizes and offsets. The banner is a centred band half the page wide (at least 480px), and each sequence diagram sits on a dark background of the same width that grows when a stage has more participants. Every table uses the same fixed columns, with long text cut off and shown in full on hover. Under each row, a sequence diagram shows who hands what to whom in that idea's stage (you, the chief-of-staff and the agents it uses): finished steps are dim, the current one is amber with a moving dot, the next ones are dashed, and a running agent glows. It's open for ideas that wait on you or are in progress, and behind "show sequence" for idle ones; what you open or close stays that way across refreshes.

The page is a dark grid of panels (it switches to a light theme when your system uses one). The top row holds big-number tiles: Waiting on you (amber), In progress (blue), Idle (grey), Agents running (green) and Done when "show finished" is ticked. Each group is a table panel whose first column is a coloured pill: red for a permission prompt, amber for a gate or your reply, blue for working. Waiting and in-progress rows also show a gate track, G1 → G-data → G2 → G3, with the gate the idea is stopped at filled in, or the next one outlined. The last panel is a state timeline for the past 60 minutes: one bar per session, blue while working, red while a permission prompt waits and amber while it waits for your reply. For that, each activity file also keeps changes, the last 50 state changes as [time, state] pairs. Every 5 seconds a few lines of inline script fetch the page again and swap the panels in, so nothing flickers; the top bar shows when it last refreshed. Everything is inline, so it works offline.

Rooms. /rooms (a "Rooms" link in the top bar) draws the same data as a top-down pixel campus. Every idea that isn't done or shelved is one character, and each running subagent stands beside its idea's character, in a shirt colour per project with a name tag. The stage picks the room: Meeting room (pitch), Lab (experiment), Workshop (ship), Library (document) and the Office for live work with no stage or a session linked to no idea. An idea waiting on you (a permission prompt, or a gate or waiting_on: user with nothing running) goes to the kitchen, with a ! bubble naming the gate; an idea with nothing live sits on the living-room couch. After a plain chat reply the character stays in its stage room with a ?. The role sets the animation (hammer, book, magnifier, laptop, clipboard, red pen, whiteboard). The page polls /api/rooms every 5 seconds, which holds no absolute file paths (ideas are project/id), and a table below the campus lists everyone as text. It has a Pause button and stays still if your system asks for reduced motion. The Zoom button shows the art twice as large (scroll to pan). Only live ideas (a session seen in the last 10 minutes) and the ideas you tick in the Ideas chooser in the top bar are in the building; every other idea sunbathes at the Pool or on a towel on the lawn, so a fresh browser starts with only the live ones inside. An idea at the pool that waits on you keeps its ! bubble. Tick "All ideas in the building" to bring everyone in. A line above the table counts who is at the pool and how many of them wait on you. The choice is saved in your browser for the address you opened, so 127.0.0.1 and localhost keep separate choices. In the API, an agent's id is its idea's key and 8 hex digits, and an unlinked session's id is s and 8 hex digits, so they stay put while others come and go. Add ?demo=1 to see a made-up campus without any data.

Replacing a whole agent for one project

# acme-analytics/.claude/agents/acme-deck-builder.md   ← your agent
# acme-analytics/.imp/project.md
agent_overrides: presenter=acme-deck-builder

Every presenter dispatch in that project then goes to acme-deck-builder. It's explicit, so it doesn't depend on which name wins in Claude Code's lookup order.

Workflow file format

---
name: campaign-postmortem
use_when: marketing asks why a campaign under- or over-performed
entry: standalone        # or a lifecycle stage: pitch | experiment | ship | document
agents: data-analyst, business-researcher, acme-campaign-analyst, presenter, reviewer
command: postmortem      # optional
---
1. data-analyst drafts response-rate queries by segment and channel (G-data)
2. acme-campaign-analyst compares against the campaign brief
3. business-researcher: likely causes, with evidence levels
4. presenter: a 6-slide post-mortem deck, assumptions slide included

Every workflow runs through the chief-of-staff, so a new one gets the gates, the evidence rules and the no-push hook automatically. If a project workflow turns out to be useful everywhere, move its file into imp's references/; it's the same format.
